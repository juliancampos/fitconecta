01 Visão geral e produto

O que é o FitConecta+, para quem existe e como gera valor.

O FitConecta+ é um marketplace que conecta profissionais autônomos de educação física a clientes que buscam treino com acompanhamento. O profissional mantém um perfil público com modalidades, bairros de atuação, preço e disponibilidade real. O cliente encontra, agenda e paga em um fluxo único. A plataforma retém 10% do valor de cada sessão; os outros 90% são destinados ao profissional.

P
Profissional autônomo

Cadastro gratuito, vitrine pública, agenda organizada e recebimento garantido. Perfil exclusivo para pessoa física (autônomo).

C
Cliente

Busca por modalidade, cidade e bairro; visualiza horários livres; agenda e paga com confirmação atrelada ao pagamento.

+
Plataforma

Intermedeia a transação, processa o split 90/10, garante a exclusividade do horário e oferece painel de gestão.

Diferencial do produto

✓

Disponibilidade real + pagamento integrado. O horário entra como pré-reserva (pending_payment) e só é confirmado na agenda após a confirmação do pagamento. O banco impede sobreposição de horários por constraint de exclusão, eliminando dupla reserva mesmo sob concorrência.

02 Arquitetura da solução

Como os componentes se conectam, do navegador ao banco e ao storage.

Camadas e responsabilidades

Frontend · Next.js 16

Entrega a landing pública, o fluxo de autenticação e as áreas logadas de cliente e profissional. O proxy.ts concentra a guarda de rotas e o encaminhamento same-origin da API. Consome a API por caminhos relativos /api/v1/*.

Backend · Core API (Go)

Centraliza regras de negócio, autenticação, disponibilidade, agendamentos, pagamentos e emissão de URLs pré-assinadas de mídia. Expõe REST em /api/v1 e healthcheck em /health.

Banco · PostgreSQL 16 (Neon)

Fonte de verdade transacional. Usa timestamptz, UUIDs, enums e a extensão btree_gist para impedir sobreposição de horários.

Storage · S3-compatível (Neon)

Armazena avatares e galeria. Uploads vão do navegador direto ao bucket via URL pré-assinada; o servidor Go não trafega binários. Leitura pública para as imagens do perfil.

Decisão central: proxy same-origin

!

No Fly.io, frontend-fit-conecta.fly.dev e backend-fit-conecta.fly.dev são sites distintos (o domínio fly.dev é public suffix). Um cookie gravado pelo backend não é enviado ao frontend, e SameSite=Strict bloqueia o envio cross-site. A solução foi o proxy same-origin: o navegador chama /api/* no próprio frontend e o Next reescreve para BACKEND_PROXY_URL. Assim o cookie fitconecta_jwt fica no domínio do frontend e a guarda de /app/* funciona.

Middlewares e operação

  • RequestID + RealIP + Logger + Recoverer do chi, com logs estruturados em JSON via log/slog.
  • CORS restritivo: origens explícitas em ALLOWED_ORIGINS (nunca *), com AllowCredentials para o cookie de sessão.
  • AuthMiddleware valida o JWT (header ou cookie) e injeta o usuário no contexto; RequireRole restringe rotas por papel.
  • Graceful shutdown em SIGINT/SIGTERM com timeout de 10 s.
  • Timeouts de leitura/escrita de 15 s e idle de 60 s.

Guarda de rotas e proxy

O arquivo frontend/proxy.ts (equivalente ao middleware no Next.js 16) tem duas responsabilidades:

  1. Proxy same-origin: requisições a /api/* são reescritas para BACKEND_PROXY_URL, mantendo o host do frontend.
  2. Guarda de autenticação: rotas /app/* exigem o cookie fitconecta_jwt; sem ele, redireciona para /auth/login.
// frontend/proxy.ts
const BACKEND_PROXY_URL = process.env.BACKEND_PROXY_URL || "";

export function proxy(request) {
  const url = request.nextUrl.clone();

  if (url.pathname.startsWith("/api/")) {
    if (BACKEND_PROXY_URL) {
      const target = new URL(url.pathname + url.search, BACKEND_PROXY_URL);
      return NextResponse.rewrite(target);
    }
    return NextResponse.next();
  }

  const token = request.cookies.get("fitconecta_jwt")?.value;
  if (!token) { url.pathname = "/auth/login"; return NextResponse.redirect(url); }
  return NextResponse.next();
}

export const config = { matcher: ["/app/:path*", "/api/:path*"] };
i

O cliente HTTP em frontend/lib/api.ts usa BASE_URL = "", ou seja, caminhos relativos /api/v1/* com credentials: "include". Assim, o mesmo código funciona em localhost (proxy direto) e em produção (proxy para o backend).

06 Autenticação e segurança

Do login até a renderização da área protegida, sem quebrar cookies entre domínios.

Mecanismos de segurança

Senhas

Hash com Argon2id, parâmetros calibrados e salt único por usuário. Nunca armazenadas em texto puro.

Sessão web

JWT em cookie HttpOnly, Secure em produção e SameSite=Strict. Logout expira o cookie com MaxAge: -1.

Autorização

Roles client, professional e admin. Middleware de role protege operações sensíveis e a posse dos recursos é validada.

Borda e dados

CORS restritivo com credenciais, queries parametrizadas via pgx, HTTPS forçado no Fly e segredos apenas em runtime.

×

Antipadrão evitado: apontar o frontend diretamente para backend-*.fly.dev. Nesse cenário o cookie fica no domínio do backend, o proxy do frontend não o enxerga e todo acesso a /app/* volta para o login. O proxy same-origin elimina essa classe de erro.

Garantia contra dupla reserva

O banco usa um intervalo tstzrange gerado e uma constraint de exclusão GiST. Dois agendamentos ativos do mesmo profissional não podem se sobrepor:

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE appointments
  ADD COLUMN period tstzrange
  GENERATED ALWAYS AS (tstzrange(starts_at, ends_at)) STORED;

ALTER TABLE appointments
  ADD CONSTRAINT no_overlap_professional
  EXCLUDE USING gist (
    professional_id WITH =,
    period WITH &&
  ) WHERE (status IN ('pending_payment', 'confirmed'));
✓

A constraint vale tanto para a pré-reserva (pending_payment) quanto para a sessão confirmada. A exclusão é resolvida no próprio banco, não dependendo de checagens na aplicação — o que elimina race conditions.

08 Mídia e Object Storage

Upload direto por URL pré-assinada, sem passar binários pela API.

Como o backend escolhe o provedor

  • Neon Object Storage: detectado pelas variáveis AWS_ENDPOINT_URL_S3, AWS_ACCESS_KEY_ID e AWS_SECRET_ACCESS_KEY, ou por STORAGE_PROVIDER=neon. Usa path-style + SigV4.
  • MinIO / PGSTY Silo (local): a API provisiona o bucket automaticamente (EnsureBucket) e configura o acesso.
  • Bucket gerenciado: no Neon, o bucket e o modo public_read são declarados em neon.ts (infra como código) e aplicados com neon deploy. A API apenas configura CORS para GET, PUT e HEAD.
i

No Neon, operações de política de bucket (PutBucketPolicy/PutBucketAcl) retornam 501. Por isso o provisionamento automático fica desligado (StorageProvision = false) e o bucket é definido via console/configuração declarativa.

Configuração declarativa do bucket

// neon.ts
export default defineConfig({
  buckets: {
    "fitconecta-images": { access: "public_read" },
  },
});

Fluxo de deploy

  1. Autenticar: fly auth login e confirmar com fly auth whoami.
  2. Migração: aplicar infra/docker/postgres/migrations/0009_admin_panel.sql e infra/docker/postgres/migrations/0010_pix_payment.sql no PostgreSQL de produção antes do deploy do backend.
  3. Backend: definir secrets e executar fly deploy em backend/core-api.
  4. Frontend: definir BACKEND_PROXY_URL e executar fly deploy em frontend; o painel é publicado em /admin.
  5. Admin: criar o administrador via cmd/admin e acessar https://frontend-fit-conecta.fly.dev/admin/login.
  6. Validar: GET /health no backend, GET /api/v1/professionals no frontend (200) e login em /admin/login.
  7. Testar login: autenticar, cair em /app/professional e confirmar o cookie no domínio do frontend.
# backend
flyctl secrets set --app backend-fit-conecta \
  DATABASE_URL="postgres://..." JWT_SECRET="..." \
  ADMIN_JWT_SECRET="..." \
  ALLOWED_ORIGINS="https://frontend-fit-conecta.fly.dev" \
  COOKIE_SECURE="true" ENV="production"

# frontend — proxy same-origin (runtime), inclui /admin
flyctl secrets set BACKEND_PROXY_URL="https://backend-fit-conecta.fly.dev" \
  --app frontend-fit-conecta

# deploy
cd backend/core-api && flyctl deploy
cd frontend && flyctl deploy
!

fly secrets set já reinicia as máquinas para aplicar o novo valor. Como BACKEND_PROXY_URL é lido em runtime, não é necessário rebuild nesse caso — basta aguardar o app voltar. Já NEXT_PUBLIC_* seria embutido no build.

i

Diagnóstico rápido: se GET /api/v1/professionals no frontend retorna 404 (página do Next) em vez de 200, o BACKEND_PROXY_URL provavelmente está vazio e o proxy caiu em NextResponse.next(). Se retorna 502, o valor existe mas o backend não está acessível. Se retorna 200, o proxy está operacional.
